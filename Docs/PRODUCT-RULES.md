# NEXORA — قواعد المنتج الملزمة

أوامر المالك المنشورة في 7 أكتوبر 2026، بتوقيت الرياض. تسري على التصميم
والتنفيذ والمراجعة والتسليم وجميع المحادثات اللاحقة. المصدر التنفيذي الوحيد
هو خط NEXORA المسموح وتحديثاته المصرح بها. هذه القواعد لا تغلق أي بوابة اختبار.

## الفكرة فقط من المرجع

«ممنوع اخذ اي كود او طريقة عمل من اللعبة فقط الفكره وتحسينها بعمق».

الرابط المرسل: `bdr-design/GlobalHoldings-iOS-Source`، فرع
`claude/global-holdings-ios-358-ayi0xf`. القراءة المسموحة وصف تجربة اللاعب
والميزات وصور المنتج فقط. لا مصدر أو طريقة تنفيذ أو schema أو عقود أو
خوارزميات أو اختبارات أو موارد تنفيذية. لا نسخ أو إعادة كتابة للكود المرجعي،
ولا clone أو بناء أو تعديل للمستودع المرجعي. إذا احتوى وصفٌ على تفاصيل
معمارية، تُستبعد من أساس القرار. قرار NEXORA يسجل حاجة اللاعب، البدائل
المصممة مستقلًا، البحث الأولي عند الحاجة، ونتيجة القياس أو حدود الدليل.

## لا عنصر بلا دورة حياة واقعية مكتملة

«ممنوع اضافة اي قسم او خيار او زر او شركة بدون دورة حياة وظيفيه واقعيه جدًا
اهم شي باللعبه الواقعية».

قبل قبول عنصر ظاهر للاعب، يحتوي عقده الوظيفي على:

| المطلوب | الدليل اللازم |
| --- | --- |
| حاجة ومالك | سبب وجود العنصر، الجهة المسؤولة، وما يستطيع اللاعب فعله فعليًا |
| دخول | صلاحيات وشروط وموارد وعقود مسبقة، مع رفض واضح عند نقصها |
| دورة حالات | إنشاء، تجهيز، اعتماد، تشغيل، إتمام أو تعليق أو إلغاء، وانتقالات محددة |
| واقع اقتصادي | زمن وموارد وتكلفة وقيود سعة واعتماديات؛ لا دخل أو إنتاج من مجرد الضغط |
| أثر قابل للتتبع | أثر تشغيلي وحسابات مالية ووثائق مترابطة، دون تكرار التسوية |
| فشل وتعافٍ | نقص الموارد، التأخير، الخطأ، الإلغاء، التعويض أو الاسترداد حيث يلزم |
| استمرار | حفظ في كل حالة واسترجاع ثم استمرار صحيح، دون مضاعفة عملية أو فقدان حق |
| قبول | سيناريو كامل، مسارات الرفض والفشل، دليل المصدر والاختبارات والقياس |

الزر يعبر عن انتقال مسموح في هذه الدورة. الحالة تعرض السبب والوقت الفعلي
والأثر؛ لا رسالة نجاح قبل نجاح العملية. القسم مسؤول عن عمليات مكتملة،
والشركة تملك موارد والتزامات وتدفقًا تشغيليًا واقتصاديًا. لا تُضاف أسماء
الصناعات أو الأقسام كزينة، ولا تُقدّم بيانات التصميم كأنها اقتصاد حي.
التصور الأولي يصف هذه الدورات؛ أي تحكم تفاعلي فيه ينفذ دورة توضيحية معلنة
ومكتملة، ولا يثبت قبول تنفيذ اللعبة.

## السلاسة وعدم الثقل قاعدة ثابتة

«يجب ان تحافظ اللعبة على السلاسه وعدم الثقل وهذا امر وقاعده ثابته في
المستودع والتنفيذ».

كل إضافة مطالبة بإثبات صحة وظيفية وسلاسة معًا. قبل تغيير المسار الساخن،
يُكتب تقدير زمن simulation thread والتخصيصات والذاكرة، ثم يبدأ micro محدود.
القياس يفصل simulation advance وservice وWAL والكاتب وزمن الحلقة الكاملة
ويحفظ المصدر والجهاز والعبء والنتائج الخام. لا تُنقل تكلفة خارج المؤقت
لتحسين النتيجة ظاهريًا. لا مسح شامل لعالم المليون على مسار واجهة المستخدم،
ولا task/actor/lock لكل أصل، ولا JSON كامل للعالم للحفظ المعتاد.

العرض والمحاكاة الاقتصادية منفصلان. تخفيف العرض عند الضغط الحراري لا
يمس الحقوق أو النتائج أو الأحداث التجارية. تسريع الساعة يعرض التقدم الذي
نُفذ فعلًا؛ لا يتجاوز التزامات أو يحذف أحداثًا. القوائم والاستعلامات والعمل
على الخريطة محدود وبحسب الجزء المطلوب. الوسائط خارج hot state وتُحمّل عند
الحاجة. لا تتوسع الوظائف على حساب زمن الاستجابة أو الذاكرة أو الطاقة.

هدف التصميم مليون أصل، مع سعة تصل لمليونين. قبول الجهاز النهائي على
iPhone 17 Pro Max فقط: 100k ثم250k ثم1M مع وظائف فعلية وواجهة وخريطة نشطتين
وفواتير وإيرادات ورواتب وصيانة وتسليم وحفظ واسترجاع. نجاح CI لا يثبت ذلك.
تُحدد ميزانيات العرض والجهاز في خطة القبول بموافقة المالك؛ لا يُستنتج PASS
من غياب القياس. عتبة R005 `overheadRatio <= 1.10` وباقي البوابات ثابتة.

## بوابة إدخال وتوسيع المنتج

أول شريحة وظيفية طيران محدودة ومكتملة. تُستخرج المكونات المشتركة من حاجة
صناعة ثانية مُثبتة، ولا يُبنى كتالوج شركات أو منصة عامة استباقيًا. أي توسع
يمر بعقد الدورة والقياس والقبول نفسه. Stage C للأداء مفتوحة مستقلًا على
S وH؛ النجاح الوظيفي الحالي لا يغلقها. تغيير تمثيل S/H يعيد A وB المرتبط
بالمصدر وTSan وK1–K10 ثم C1M/100 للتخطيط المحدد. لا نتائج إغلاق ولا دمج main
قبل PASS حقيقي ومراجعة قرار المالك. Stage2–4 وiPhone وIPA تأتي بعد هذه البوابة.
